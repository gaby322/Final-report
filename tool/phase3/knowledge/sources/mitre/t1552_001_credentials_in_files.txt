SOURCE: MITRE ATT&CK® for Enterprise (Cloud) — Technique T1552.001
TECHNIQUE: Unsecured Credentials: Credentials In Files
TACTIC: Credential Access
ATT&CK ID: T1552.001
URL: https://attack.mitre.org/techniques/T1552/001/
NOTE: Curated synthesis of MITRE ATT&CK wiki content and AWS IAM/EC2 metadata documentation.

DESCRIPTION:
Adversaries may search the file system and file contents for insecurely stored credentials.
In AWS environments, this includes access keys stored in EC2 instance user data, hardcoded
credentials in Lambda environment variables, credentials in S3 object contents, IAM
credentials cached in ~/.aws/credentials on EC2 instances, and instance metadata service
(IMDS) token exposure.

RELEVANT AWS EXPOSURE VECTORS:
- EC2 instance user data (ec2:DescribeInstanceAttribute) — sometimes contains plaintext credentials
- Lambda environment variables (lambda:GetFunctionConfiguration) — may contain API keys
- SSM Parameter Store (ssm:GetParameter) — may contain secrets if not using SecureString type
- Secrets Manager (secretsmanager:GetSecretValue) — legitimate secrets store (monitor access)
- S3 object contents with access keys (s3:GetObject on credential files)
- EC2 Instance Metadata Service v1 (IMDSv1) — no token required, exploitable via SSRF

IAM-SPECIFIC RELEVANCE:
From an IAM perspective, this technique intersects with:
- Roles with lambda:GetFunctionConfiguration on * (enables reading env vars for all functions)
- Roles with ec2:DescribeInstanceAttribute (enables reading instance user-data)
- Overly permissive SSM parameter read access (ssm:GetParameter on *)
- IMDSv1 enabled on EC2 instances (allows credential theft via SSRF without IAM permission)

EC2 IMDSv2 (token-required mode) mitigates SSRF-based credential theft. IMDSv1 without
PUT token requirement remains a critical IAM exposure risk for workload roles.

DETECTION IN THIS FRAMEWORK:
Phase 3 correlates lambda:GetFunctionConfiguration and ssm:GetParameter calls against
principals with Phase 2 escalation paths. Principals performing broad enumeration of
Lambda environment variables or SSM parameters after obtaining elevated credentials
indicate post-escalation credential harvesting activity.

REMEDIATION POINTERS:
- Enforce IMDSv2 on all EC2 instances. Set the EC2 instance metadata option
  HttpTokens=required via the ec2:ModifyInstanceMetadataOptions API, and
  optionally restrict non-required values using the ec2:MetadataHttpTokens
  IAM condition key (service prefix ec2:, not aws:).
- Never store credentials in Lambda environment variables; use Secrets Manager
- Apply SCP denying ec2:ModifyInstanceMetadataOptions to prevent downgrade to IMDSv1
- Restrict ssm:GetParameter to specific parameter paths using resource conditions
- Enable Secrets Manager rotation and access logging
