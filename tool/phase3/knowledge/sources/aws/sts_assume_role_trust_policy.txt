AssumeRole overview:
sts:AssumeRole is an AWS STS API operation that returns temporary security credentials for an IAM role. To assume a role, the caller must be trusted by the role’s trust policy, and in many scenarios the caller also needs an identity-based policy that allows sts:AssumeRole on the target role.

Trust policy structure:
A trust policy is a required resource-based policy attached to an IAM role. It specifies which principals are trusted to assume the role. AWS documents that principals in a role trust policy can include AWS accounts, IAM users, IAM roles, federated principals, and AWS services.

Useful trust-policy conditions:
Commonly used condition keys in trust policies include:
- aws:MultiFactorAuthPresent
- aws:PrincipalOrgID
- sts:ExternalId
Additional IAM and STS condition keys can be used depending on the trust model.

Broad trust risks:
A trust policy can become overly broad if it trusts an entire external account or uses a very broad principal scope without restrictive conditions. AWS also documents that wildcard use in the Principal element has important limitations and risks, and recommends narrowing access with conditions where broader trust is unavoidable.

Cross-account trust:
For cross-account role assumption, the trusting account uses the role’s trust policy to specify the trusted account or principal, and the trusted side must also grant the caller permission to call sts:AssumeRole. Both sides matter.

Role chaining:
A role session can assume another role if the session has permission to do so and the target role’s trust policy allows it. This is operationally relevant to multi-hop access paths.

UpdateAssumeRolePolicy:
iam:UpdateAssumeRolePolicy replaces the trust policy attached to a role. In security analysis, this is a high-impact action because a principal that can modify trust policy can potentially expand who is allowed to assume the role.
