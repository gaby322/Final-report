Overview:
AWS policy conditions are evaluated against the request context. A Condition element can compare request attributes against global condition keys or service-specific condition keys.

Condition-key categories:
- Global condition keys use the aws: prefix.
- Service-specific condition keys use a service prefix such as iam: or sts:.
- IAM and AWS STS also support IAM-specific and STS-relevant condition context keys for trust, tagging, and identity controls.

Examples relevant to IAM security:
- aws:MultiFactorAuthPresent can be used to require MFA context
- aws:PrincipalOrgID can restrict access to principals in a specific AWS Organization
- aws:SourceAccount can help limit service-to-service confused-deputy exposure in supported patterns
- sts:ExternalId is used in third-party cross-account role assumption scenarios
- aws:ResourceTag and iam:ResourceTag can be used in tag-aware authorization logic

ABAC relevance:
Tag-aware authorization can use aws:PrincipalTag, aws:ResourceTag, aws:RequestTag, and aws:TagKeys. These keys are important when access decisions depend on tags attached to principals or resources.

Trust-policy relevance:
Condition keys are often critical in role trust policies. Even when a principal is listed in the Principal element, conditions may still be required to limit assumption to expected callers, organizations, or MFA-authenticated sessions.
